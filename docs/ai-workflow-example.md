# Worked example: Bill Pay, from user story to reviewed tests

One real run of the AI-assisted workflow, end to end: a user story goes in, an AI draft comes out,
the review finds what the draft got wrong, and the fix feeds back into the instructions. The
draft and the reviewed version are separate commits, so the history shows exactly what the review
changed.

| Step             | Artifact                                                                                                                                        |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Input            | [ai-demo/bill-pay-story.md](ai-demo/bill-pay-story.md): user story + 5 acceptance criteria                                                      |
| Generation       | `/generate-ui-test` ([ai/generate-ui-test.md](../ai/generate-ui-test.md) v1.0.0), log in [ai-demo/generation-log.md](ai-demo/generation-log.md) |
| AI draft         | commit `test(ai-draft): add Bill Pay UI tests generated by /generate-ui-test`                                                                   |
| Review           | [ai/review-ai-tests.md](../ai/review-ai-tests.md) v1.0.0 (this page)                                                                            |
| Reviewed version | commit `test(bill-pay): apply review of AI-generated Bill Pay tests`                                                                            |

## 1. Generation

A headless Claude Code run (`claude-opus-5-5`, Claude Code 2.1.284) executed the command with the
repo's `.mcp.json` (Playwright MCP 0.0.83). It had an explicit tool allow-list.
`browser_evaluate`, `browser_run_code_unsafe`, `git commit` and `git push` were denied, so the
agent could explore and edit but not script the page or commit. The run took 51 turns and about
3.5 minutes (Claude Code reported an estimated cost of $1.15).

What the agent did, in order (full list in the generation log):

1. Read `CLAUDE.md`, `docs/KNOWN-ISSUES.md` and the existing page objects and fixtures.
2. Registered its own customer in the browser and explored `billpay.htm` with Playwright MCP:
   10 snapshots, 6 clicks, 3 form fills, and 3 network-request inspections.
3. Tried the negative paths for real (empty form, mismatched account numbers, a negative amount).
4. Wrote `BillPayPage`, a `PayeeBuilder`, a `billPayPage` fixture and three tests. Ran
   `npm run check` and the tests (9/9 with `--repeat-each=3` on chromium, 10/10 on all projects).
5. Reported its scenario table, locator choices, and one **suspected defect**: a negative bill
   payment adds money to the account. It did not write a test for it, because the story didn't
   cover it, and it asked instead.

## 2. What the draft got right

These points were checked by reading the code and running it, not taken from the AI's report:

- **Locators follow the ladder, and each reason is true.** The inputs have neither labels nor ids
  (checked in the snapshot), so `[name=…]` with a comment is correct. The validation messages are
  found through `getByRole('row').filter({ has: getByRole('cell', { name: label }) })`, which ties
  each message to its field. That matters because _"Account number is required."_ appears on two
  rows.
- **The happy path proves behaviour, not the banner.** It pays from a _non-default_ account, so a
  bug that always charged the pre-selected account would fail the test. It then checks through the
  API that exactly that account was debited, the other account is untouched, and the ledger has a
  `Debit` with the payee's name.
- **Every acceptance criterion maps to an assertion.**
- **The suspected defect was real.** Reproduced independently over REST (`amount=-5` → balance
  100.00 → 105.00). Now [KNOWN-ISSUES.md #7](KNOWN-ISSUES.md).

## 3. Review

### Machine checks

| Check                                   | Result |
| --------------------------------------- | ------ |
| `npm run check` (prettier, eslint, tsc) | pass   |
| chromium `--repeat-each=5`              | 15/15  |
| all projects                            | 10/10  |

### Sensitivity check: does each assertion fail when it should?

Each key assertion was broken on purpose in a temporary copy of the spec:

| Mutation                                | Result   |
| --------------------------------------- | -------- |
| Expected debit off by 1 cent            | failed ✓ |
| "Other account unchanged" off by 1 cent | failed ✓ |
| Confirmation names the wrong account id | failed ✓ |
| Ledger description wrong                | failed ✓ |
| Required-field message wrong            | failed ✓ |
| Mismatch message wrong                  | failed ✓ |

**Reverse negative control** for the two "no payment is made" tests: make the payment _succeed_
(matching account numbers), remove the error-message assertion, and check that the "nothing
changed" assertions catch it. Over 10 runs:

| Assertion in the draft                      | Caught the real payment                                         |
| ------------------------------------------- | --------------------------------------------------------------- |
| `await expect(successHeading).toBeHidden()` | **0/10**: it passes instantly, before the AJAX call returns     |
| balance unchanged (API)                     | **5/10**: the balance was read before the payment was applied   |
| transactions unchanged (API)                | 5/10, only in the runs the balance check missed, by timing luck |

### Hypothesis checked and rejected

About 3% of faker company names contain `'` (and some contain `&`), and they reach both the
confirmation text and the ledger description. Forcing `O'Hara Group` and a 47-character name with
`'` and `&` through the happy path passed, so this is not a risk.

### Findings

| #   | Sev   | Location                                | Finding                                                                                                                                                                   | Fix                                                                                                                                                                           |
| --- | ----- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **B** | `bill-pay.spec.ts`, both negative tests | "No payment was made" was not actually proven: `toBeHidden()` proves nothing, and the API checks race the AJAX request (reverse control caught the payment 0/10 and 5/10) | `BillPayPage` records `/billpay` requests. Tests first wait for the validation message, then assert that no payment request was sent. API checks stay as a final ledger check |
| 2   | m     | `bill-pay.spec.ts` (empty form)         | Spec clicked `billPayPage.sendPaymentButton` directly while `pay()` owned submission                                                                                      | Added `BillPayPage.submit()`, used by `pay()` and the spec                                                                                                                    |
| 3   | —     | suspected defect                        | Negative amount credits the account                                                                                                                                       | Verified; recorded as KNOWN-ISSUES #7. A `@known-defect` API test is deferred to a `/generate-api-tests` run for `POST /billpay`                                              |

After the fix, the reverse negative control catches the payment **10/10** at the new assertion.
The suite still passes 15/15 (chromium ×5) and 10/10 on all projects.

### Before / after (finding 1)

```ts
// AI draft
await expect(billPayPage.fieldRow('Verify Account #:')).toContainText(
  'The account numbers do not match.',
);
await expect(billPayPage.successHeading).toBeHidden(); // passes instantly: proves nothing
const after = await api.accounts.getAccount(customer.primaryAccountId); // races the request

// Reviewed
await expect(billPayPage.fieldRow('Verify Account #:')).toContainText(
  'The account numbers do not match.',
);
expect(billPayPage.paymentRequests).toEqual([]); // the precise proof
const after = await api.accounts.getAccount(customer.primaryAccountId); // final ledger check
```

**Verdict:** approve after fixes.

## 4. Feedback into the instructions

Finding 1 is a general pattern ("absence of an effect" asserted with a check that can't fail), not
a one-off, so it went back into the workflows:

- `ai/generate-ui-test.md` **1.1.0**: a rule for proving that nothing happened, plus a checklist
  item.
- `ai/review-ai-tests.md` **1.1.0**: the reverse negative control as a procedure step, plus a
  blocker-level checklist item.

## Takeaways

- The draft was good, and it would have passed a casual review and CI: all green, sensible
  locators, API-verified happy path. The weakness only showed when its assertions were made to
  fail on purpose.
- Two things are delegated to the AI: exploring the app and writing the first draft. Two stay
  human-owned: deciding what counts as proof, and deciding what to do with a suspected defect.
